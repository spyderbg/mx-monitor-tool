# Verified Worker compatibility — M1

The adapter `mx-feature-worker/w4-v1` was derived read-only from the local `../mx-admin-cloud/scripts/feature_coordinator/` implementation, with W4/W4.1/W4.2 behavior described in `../mx-admin-cloud/docs_agents/coordination/worker-autonomy.md`. No Python module was imported or executed. No Worker service, CLI, agent or model was started. `build/m1-external-source-before.json` records inspected source hashes; final verification compares them without writing to the external project.

| Allowlisted source | Verified format and source definition | Projected data |
|---|---|---|
| `service/worker.json` | schema v1; `autonomy.py::ServiceRecord`, `service.py` writers | Persisted state, PID/start/boot identity, timestamps, current feature/task/role/provider/requested model/step, sanitized reason, last recorded checkpoint. |
| `features/<id>.json` | schema v1; `model.py::Feature` | ID, state, task IDs. No instructions, workspace, PR or acceptance content. |
| `tasks/<id>.json` | schemas v1/v2; `model.py::Task`, `migrate_task_record` | ID/feature/role/state, dependencies, step keys, last state-change time, sanitized blocked reason. v1 explicitly has no steps. |
| `claims/<task>.json` | Verified unversioned `claims.py::Claim.to_dict`; `native_backend.py` records agent identity | Task/feature/role relationship, holder and agent identities, step, heartbeat. Tokens, run tags/directories and branch details are discarded. |
| `checkpoints/<task>.json` | schema v1; `checkpoints.py::CheckpointRecord` / `Checkpoint` | Matching task/feature/role/steps, bounded history, sequence, status, provider/requested model, short recorded commit, timestamp, completed steps excluding superseded checkpoints. No summaries, prompts, file manifests, local paths, notes or gate logs. |
| `scheduling/<task>.json` | schema v1; `autonomy.py::Scheduling` | Launch count, failure-attempt count, next-attempt timestamp, sanitized attention/wait reason/category. Actual retry count cannot be inferred reliably and remains null. |
| `events.jsonl` | Verified unversioned `{at, kind, ...}` writer in `store.py::append_event`; known emitters in service/claims/checkpoints | UTC timestamp, supported event kind, safe feature/task IDs, fixed summary and derived severity. All raw free-text payloads are omitted. |

No other state filename is read. In particular the Monitor does not read `auth`, credentials, transcripts, prompts, run files, Worker configuration, locks, GitHub/outbox records, startup failure records or process environments. `flags/worker-control.json` is unnecessary for observation and is not opened. Service states already represent PAUSED/STOPPING.

Service/scheduling/checkpoint/task schema revisions and required projected fields are validated. Unsupported schema versions, unknown strict record fields, mismatched IDs/roles/steps and malformed values are refused. Feature projection validates its known v1 fields. Claim and event files have no declared version; compatibility is limited to the inspected writer shape and allowlisted kinds. Unknown events are omitted with a source warning rather than guessed. New external revisions require re-verification, never an invented adapter.

Worker service liveness requires the recorded PID **and** start ticks **and** Linux boot UUID to match a non-zombie `/proc/<pid>/stat` observation. Fresh heartbeat is a separate condition. AVAILABLE maps to RUNNING; verified fresh BUSY/WAITING/PAUSED/RECOVERING/NEEDS_ATTENTION/STOPPING retain their meanings. A dead/mismatched identity or persisted OFFLINE means OFFLINE. Inaccessible/incomplete identity means UNKNOWN. A live identity with old/missing/future heartbeat means STALE. Historical current-run fields are never shown as a live run after OFFLINE/UNKNOWN/STALE. Service identity and task/agent identity are checked independently.

The Monitor's default service freshness threshold is 90 seconds, matching 3 × the Worker's **default** 30-second heartbeat. The Worker configuration is not read, so set `MX_MONITOR_TOOL_WORKER_STALE_MS` if its configured heartbeat differs. Claim silence uses the inspected default 120-second threshold and is labeled slow/unverified; it never triggers an action. Liveness checks do not read executable arguments or run tags from environments. Descendant discovery uses only known parents' `task/<pid>/children`, validates parent/start evidence, and is capped at depth 4 / 64 rows. Same-named unrelated processes are not scanned or attributed. Detached processes without recorded identity/verified ancestry are intentionally not discovered.

Files are opened read-only and nonblocking through pinned Linux directory FDs, with `O_NOFOLLOW` on each untrusted component. Symlink roots/components/files, hard-linked files, traversal, special file kinds and oversized records are refused. Explicit configured parent aliases may resolve to the chosen root, but the root itself and all subsequently opened state components cannot be symlinks. No Worker locks are acquired and no directory is created. Atomic replacements retain old FD contents safely; missing/malformed reads produce explicit errors/stale states and recover on later samples. No cross-file Worker transaction is taken: snapshot coherence is a Monitor collection boundary, not a claim of atomic consistency across simultaneous Worker writes.

Limits: records 256 KiB, JSON nesting 16, tasks 128, features 64, directory entries scanned at most 2 × the record cap per kind. A task source supports up to 20 steps and 256 source checkpoints; displayed history is 20/task and 400 globally. Process observation is 64 rows/depth 4. Events retain 100 items and 512 dedup fingerprints, read at most 128 KiB/cycle, and reject lines above 16 KiB. Initial large logs begin at a bounded tail, skipping an incomplete leading line; truncation is signaled. Event rotation uses root/device/inode, size and prefix checks; malformed/incomplete lines are never emitted as events. A truncate-and-regrow operation that preserves the exact checked prefix and grows beyond the old offset between samples may be indistinguishable from append; this polling limitation is explicit.

Real observation in this environment: the conventional root existed, but its feature/task directories were empty and it had no service, scheduling, checkpoint or event records. The documented W4.2 default smoke-run directory had no run samples. The live UI correctly reports the Worker as UNAVAILABLE with no verified live activity. Verified live/BUSY, offline, stale, permission failure, orphaned agent, PID reuse, tasks/checkpoints and events are exercised with **clearly synthetic fixtures matching the inspected source**, not presented as production Worker evidence. A separately configured actual state root can be observed without changing Worker.
